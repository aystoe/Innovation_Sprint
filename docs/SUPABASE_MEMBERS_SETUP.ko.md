# Members·프로필 Supabase 연결 — 3단계

현재 프로필 등록/수정, Members 목록과 필터, 본인 및 타인 프로필 상세, 사진이 Supabase 데이터로 연결된다. 기존 CSS, 사진 에셋, 카드·필터·프로필 폼 구조는 유지했고 기존 버튼 스타일로 페이지 이동을 추가했다. 가입은 이전 단계의 TUM 도메인·앱 비밀번호 방식을 유지한다.

## 적용 순서

1. 앞 단계 001–004 migration과 Auth 설정을 먼저 적용한다.
2. `supabase/migrations/202611100005_member_directory.sql`을 적용한다. SQL Editor에 파일 전체를 실행하거나 CLI migration으로 적용한다. RLS가 적용된 `featured_members`, 검색/필터 옵션 RPC, 인덱스를 추가한다. `avatars`는 private, JPEG/PNG/WebP, **5 MiB**로 제한한다.
3. `.env.local`에 기존 Supabase URL·publishable key와 **`VITE_DATA_MODE=production`**을 설정하고 개발 서버를 재시작/다시 빌드한다. 값이 없거나 잘못된 값이면 운영 모드가 기본이다. Secret/service-role 키는 브라우저 환경변수에 넣지 않는다.
4. `npm install`, `npm run test`, `npm run lint`, `npm run build`로 검증한다. 현재 실행 환경에서는 npm registry가 403을 반환해 전체 설치·빌드·React 테스트는 실행하지 못했다. 기존 단계와 마찬가지로 최초 npm install로 lockfile을 생성한 뒤 이후부터 npm ci를 사용한다.
5. 실제 회원 2명 이상으로 가입·프로필 저장 → 검색/필터 → 타인 상세 → 본인 수정 → 재조회로 반영 여부를 확인한다.
6. 아래 절차로 실제 팀원 UUID를 연결한다. 이번 작업에서는 실제 계정 목록/DB 연결이 제공되지 않아 특정 팀원 계정을 추측해서 연결하거나 원격 DB를 변경하지 않았다.

## 팀원 계정 연결과 순서

`public.featured_members`는 `user_id → profiles.id → auth.users.id` FK로 연결된다. 해당 계정이 실제 가입하고 프로필을 작성해야 팀원으로 지정할 수 있다. 이름/기존 `team-leonie` 등의 문자열 ID/하드코딩 사진으로 매칭하지 않는다. 기존 팀원 샘플 프로필을 실계정으로 자동 가져오지도 않는다.

**관리자는 Supabase 프로젝트를 관리하는 운영자**다. 앱의 Organizer 화면을 선택했다고 관리자가 되는 것이 아니다. `user_roles`를 만들거나 기존 Member/Organizer 권한 모델을 바꾸지 않았다.

1. 각 팀원이 자신의 TUM 이메일로 가입하고 본인 이름·프로필·사진을 등록한다.
2. Supabase Dashboard → Authentication → Users에서 운영자가 실제 계정의 UUID를 확인한다. `public.profiles`에 같은 UUID가 있는지도 확인한다. 회원에게 이메일이나 Auth 목록을 조회시키는 API는 만들지 않는다.
3. Dashboard → Table Editor → `featured_members`에 `user_id`와 `display_order`를 입력한다. 숫자가 작을수록 먼저 표시되고, 같은 순서를 두 명에게 줄 수 없다. 프로필별 1행만 허용한다.
4. 여러 명을 한 번에 재정렬하려면 관리자 DB 연결에서 제공한 스크립트를 실행한다.

```bash
psql "$ADMIN_DB_URL" -X -v ON_ERROR_STOP=1 \
  -v member_ids='["실제-첫번째-사용자-UUID","실제-두번째-사용자-UUID"]' \
  -f supabase/admin/set_featured_members.sql
```

이 스크립트는 전달한 목록 순서대로 **전체 팀원 고정 목록을 교체**한다. 배열에서 빠진 사람은 고정만 해제되고 계정/프로필은 삭제되지 않는다. `[]`는 전체 고정 해제다. 잘못된 UUID, 프로필 미작성 계정, 중복 계정은 트랜잭션을 실패시켜 기존 목록을 보존한다. service-role을 사용하는 신뢰된 서버에서도 관리할 수 있으나 일반 브라우저에는 쓰기 권한이 없다.

팀원도 검색·필터 조건을 만족해야 나타난다. 결과 전체를 `display_order ASC NULLS LAST → 정규화 이름 → UUID`로 정렬한 **뒤** 페이지를 나눈다. 팀원이 여러 페이지에 걸쳐 있을 수 있으며 모든 페이지마다 같은 팀원을 중복 표시하지 않는다. 본인 프로필 편집으로 팀원 순위를 바꿀 수 없다. 운영자의 순서 변경은 다음 조회/새로고침에 반영된다.

## 서버 검색·필터·페이지네이션

- `search_members`: 인증된 회원만 호출 가능. `SECURITY INVOKER`라 기존 프로필 RLS와 팀원 RLS를 그대로 적용한다. `auth.users`를 조회하거나 이메일/토큰을 복사하지 않는다.
- 이름 검색: 대소문자·반복 공백·일반적인 라틴 악센트를 정규화하고, 검색어의 모든 단어가 이름에 포함되어야 한다. `%`, `_`, 쉼표 등은 검색 문자열 그대로 취급하며 SQL/PostgREST 필터 구문으로 삽입하지 않는다.
- 직업·전공: 정규화 후 전체 값 일치.
- 수강 과목: 쉼표/세미콜론/줄바꿈으로 분리한 개별 과목 전체 값 일치. `ML` 검색으로 `ML Advanced`를 매칭하지 않는다.
- 관심사: 기존 Members 화면 의미를 유지해 `interests` 입력과 `topics` 태그를 합친 값에서 선택 관심사 중 하나 이상 일치(OR).
- 서로 다른 필터 종류와 이름 검색은 AND. 연락 선호 필터도 서버에서 처리한다.
- `member_filter_options`는 전체 실제 프로필에서 중복을 제거해 선택지를 만든다. 현재 페이지 20명만 보고 선택지를 제한하지 않는다.
- 입력 변경 후 **300ms debounce**. 조건이 바뀌면 1페이지부터 조회한다. 진행 중인 DB 요청은 abort하고, 완료된 이전 요청도 취소 상태를 검사해 늦은 결과를 버린다.
- **페이지당 20명**, 서버 상한 50명. total과 page 결과는 한 SQL statement의 동일 스냅샷에서 계산하므로 빈 페이지에도 total이 제공된다. 페이지 이동 중 회원이 삭제되어 범위를 벗어나면 마지막 유효 페이지로 이동한다.
- 목록을 전부 브라우저에 가져온 뒤 필터/정렬하지 않는다. 사진도 해당 페이지에 대해서만 최대 4개씩 병렬 download한다.
- 네트워크/DB 오류는 오류·재시도 상태로 표시한다. 오류 때 가짜 회원을 대신 표시하지 않는다. 사진 한 장이 없어도 전체 목록·프로필 접근을 막지 않고 기본 이미지를 표시한다.

이번 구현은 offset pagination이다. UUID를 포함한 안정적인 정렬로 동명이인의 순서가 뒤섞이지 않는다. 단, 서로 다른 페이지 요청 사이에 프로필·팀원 순서가 변경되면 offset 위치도 변할 수 있다. 실시간 스냅샷 고정은 구현하지 않았다. 이름 포함 검색의 `strpos`와 전체 distinct 옵션 집계는 큰 데이터셋에서는 스캔 비용이 있으므로 대규모 배포 시 EXPLAIN/검색 인덱스 또는 cursor pagination을 검토한다. 현재 추가한 인덱스는 정규화 직업/전공, 과목·관심사 배열 GIN, 이름/UUID 정렬용이다.

## 프로필·사진·개인정보

- 등록은 본인 UUID로 INSERT, 수정은 본인 UUID로 UPDATE. 기존 RLS/컬럼 GRANT로 타인 수정과 UUID 변경을 막는다.
- 상세 화면은 선택한 UUID로 서버의 프로필을 조회한다. 로그인 이메일 필드는 프로필 테이블에도 검색 RPC에도 없다. 공개 `social`/`social_other`에 회원이 자발적으로 입력한 정보는 로그인 이메일과 별개다.
- 타인의 출석 이력을 읽기 위해 RLS를 우회하지 않았다. 기존 프로필 통계 위치에는 비공개 안내를 표시하고 허구의 출석 수를 표시하지 않는다.
- 기존 PhotoPicker에서 JPEG/PNG/WebP만 선택할 수 있고 원본 **5 MiB**를 초과하면 거부한다. 브라우저에서 이미지를 실제 decode 후 canvas로 JPEG 재인코딩한다. repository도 형식/크기를 다시 검사한다.
- 비공개 avatars 버킷에 `<현재 UUID>/<랜덤 UUID>.<확장자>`로 저장한다. 저장된 경로를 연결한 프로필을 읽을 수 있는 회원만 해당 파일을 읽는다. 업로드/교체/삭제는 기존 owner_id·경로 RLS로 본인에게만 허용한다.
- Supabase 버킷 설정이 직접 API 업로드에도 MIME/용량을 제한한다. MIME 검사는 서버의 바이너리 분석/악성파일 검사와 동일하지 않으며, 별도 서버 이미지 처리 작업은 추가하지 않았다.
- 새 사진 업로드 → DB 경로 저장 → 옛 사진 삭제 순서다. 서버가 명확한 DB 제약 오류를 반환하면 새 사진을 정리한다. 결과를 알 수 없는 네트워크 오류에서는 저장됐을 가능성이 있어 즉시 삭제하지 않는다. 이런 고아 파일은 향후 정리 작업 대상이다.
- DB 갱신 후 옛 파일 삭제 실패는 경고로 구분한다. 사진 로드 실패 시에도 본문 편집은 가능하며 기존 경로를 임의로 지우지 않는다. 등록/수정 폼에 저장된 사진을 제거하거나 새 사진으로 교체하는 방법을 제공한다.

## 운영 모드와 범위

`VITE_DATA_MODE=production`이 기본이다. SAMPLE_PROFILES/TEAM_PROFILES를 운영 중 회원 목록에 합치지 않는다. 기존 팀원 이름·프로필 사진도 실계정의 프로필을 대체하지 않는다. Members 목록과 프로필 상세는 demo 설정에서도 항상 서버의 실제 회원을 사용한다.

이전 단계에 남아 있던 행사·채팅·요청 샘플은 `demo`를 명시했을 때만 쓰는 별도 메모리 데이터다. 운영 모드는 가짜 회원/샘플 행사/샘플 요청을 초기화하지 않는다. 아직 서버에 연결하지 않은 행사 작성·채팅·요청 액션은 성공했다고 가장하지 않고 미연결 안내를 반환한다. 화면 전환 버튼·메뉴·Organizer 레이아웃은 유지하며, 샘플 KPI는 기존 sample data 표시를 유지한다. Organizer 사람 찾기/채팅 전체의 실제 서버 연결은 이 요청의 Members 디렉터리·프로필 범위 이후 단계다.

가입 이메일 인증 OFF 설정은 바꾸지 않았다. 따라서 “실제 가입자”는 Auth 계정과 profiles를 가진 사용자를 의미하며, 메일함 소유권이나 재학 신분 검증을 의미하지 않는다.

## 검증

실행 완료:

- Node 단위 테스트 **27개 통과**: 기존 인증 22개 + 검색 파라미터·페이지·특수문자·필터 키 테스트 5개.
- TypeScript `.ts` 파일 구문 검사와 로컬 import 경로 확인. TSX 타입 검사/실행 검증을 대신하지 않는다.
- 기존 CSS 및 001–004 migration 무변경 확인.

작성했으나 실행 환경 제약으로 미실행:

- `tests/memberDirectory.test.tsx`: debounce, 조건 변경 시 첫 페이지, 요청 경합·취소, 오류 시 샘플 fallback 금지.
- `supabase/tests/member_directory.sql`: 서버 검색, AND/OR, 전체 옵션, 동명이인 페이지 분리, 팀원 우선 정렬·필터, 관리자만 순서 변경, 익명 조회 차단, 이메일 필드 부재. 폐기 가능한 빈 테스트 DB에서 001–005 적용 후 실행하고 rollback한다.
- 실제 Storage/API/브라우저 빌드 검증: npm registry가 403이고 DB 자격 증명도 없어 수행하지 못했다. 운영 배포 전 아래를 확인한다.

수동 확인:

1. 실제 가입·프로필 작성 21명 이상 → 20/1명 페이지 분리. 프로필 없는 가입 계정은 디렉터리에 나오지 않음.
2. 빠른 연속 타이핑, 2페이지에서 필터 변경, 느린 이전 응답이 나중에 도착하는 조건을 확인.
3. 본인 프로필 수정 후 Members 재진입 시 이름/필터 옵션/사진 반영. 타인 상세는 해당 실제 프로필과 일치.
4. 일반 회원 및 Organizer 화면에서 featured_members INSERT/UPDATE/DELETE를 직접 시도하면 모두 거부.
5. 관리자가 팀원 순서를 바꾸면 전체 검색 결과의 순서가 바뀌고, 필터에 맞지 않는 팀원은 나타나지 않음.
6. 검색 RPC JSON에 email/email_change/Auth metadata가 없음.
7. 5 MiB 초과·SVG·위장 파일을 UI에 넣었을 때 거부. 직접 Storage API에서는 MIME/용량 정책을 확인.
8. 타인이 공개 프로필 사진을 읽을 수 있어도 업로드 덮어쓰기/삭제/다른 UUID prefix 업로드는 실패.
9. 사진 삭제·파일 404·오프라인 시에도 타인의 다른 프로필 정보는 읽을 수 있고, 검색 실패 시 가짜 목록을 표시하지 않음.
